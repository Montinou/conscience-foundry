# F1 guide: commands, evidence and open gates

This guide describes how to reproduce the F1 offline acceptance evidence, what that evidence does
and does not prove, and which gates are still `not_run`. It contains no real endpoint, credential,
tariff, path or account; every value shown is a placeholder in angle brackets.

## 1. Evidence labels

Every claim in a report or review carries exactly one label.

| Label | Meaning |
| --- | --- |
| `synthetic_offline` | Ran in-process against synthetic fixtures and fake transports. No service, network, provider or real cost. |
| `local_isolated_postgres` | Ran against a disposable local PostgreSQL that the operator explicitly authorized (section 5). Nothing else is reached. |
| `not_run` | Needs authority, infrastructure or a later phase that does not exist yet. It is never reported as success. |
| `blocked` | A prerequisite is missing (a locked dependency, a required value, a gate). The check stops; it is never skipped or replaced by a weaker check. |

Test outcomes are `pass`, `fail` or `not_run`. A command-line outcome is `ok`, `dry_run`,
`failed` or `blocked`. The `cfoundry` command exits 0 (ok or dry run), 1 (failed), 2 (usage) or 3
(blocked by a gate). The standalone parity tools use their own codes: `node tests/js/schema_parity.mjs`
and `scripts/check_schema_parity.py` exit 0 (parity holds), 1 (a check failed) or 2 (blocked by a
missing toolchain or dependency, or by a Node timeout in the Python wrapper); `scripts/check_public_boundary.py` exits 0 (boundary
holds) or 1 (a violation).

## 2. Locked toolchain

| Tool | Pin |
| --- | --- |
| Python | 3.12, with `uv` managing the environment from `uv.lock` |
| Build backend | `setuptools>=80,<81` |
| Python canonical JSON | `rfc8785>=0.1.4,<0.2` |
| Node | 22 or newer (`tests/js/package.json` `engines`) |
| JSON Schema validator (Node) | `ajv@8.20.0`, JSON Schema 2020-12 dialect |
| Canonical JSON (Node) | `canonicalize@5.1.0`, an RFC 8785 implementation separate from the Python one |

The Node tools are development-only, locked with exact versions and integrity hashes in
`tests/js/package.json` and `tests/js/package-lock.json`. `node_modules` is never committed.
Install from the lock with `npm ci` inside `tests/js` (use `npm ci --offline` when the packages are
already in the local npm cache). A missing dependency is `blocked`: the parity checker exits 2 (not 3, which is the `cfoundry` code) and
the Python wrapper raises `NodeToolchainBlocked`. It is never skipped, and a Python-only check
never stands in for it.

## 3. Verification commands

All of these are `synthetic_offline` unless stated otherwise.

```
uv run ruff check .
uv run mypy src/conscience_foundry
uv run pytest tests/acceptance/test_public_package.py -q
node tests/js/schema_parity.mjs
uv run python scripts/check_schema_parity.py
uv run python scripts/check_public_boundary.py [<wheel-or-sdist> ...]
uv run pytest                      # full suite; database tests need section 5
```

- `node tests/js/schema_parity.mjs` compiles every exported schema in `schemas/` with Ajv (the
  raw byte roles `kf.raw-original.v1` and `kf.canonical-text.v1` are exported as `{"not": {}}`:
  they compile but no JSON instance validates, so they are outside JSON-instance parity; the
  report lists them separately as `outsideInstanceParity`, and the Python checker asserts that
  exact set),
  validates the shared fixtures (`tests/fixtures/public/schema_parity.json`) and checks canonical
  bytes and SHA-256 digests against literal expectations. It imports no repository code.
- `uv run python scripts/check_schema_parity.py` runs the Node checker, runs the maintained
  Pydantic models over the same fixtures and fails on any disagreement. `semantic_invalid`
  fixtures are shape-valid JSON Schema instances that trusted semantic code rejects (for example an
  empty span, a lone surrogate or a cross-project reference); the split is asserted, not hidden.
  array length bounds are in the exported schemas (see "Array bounds in the exported schemas"), so
  an empty or over-length array is a plain `shape_invalid` fixture that Python and Ajv both reject.
  Ajv runs fully strict (`strict` and `strictTypes`), so a bound keyword on the wrong type fails
  compilation.
- Canonical JSON follows RFC 8785: object keys sort by UTF-16 code unit, so U+10000 sorts before
  U+E000 (code point order would reverse them). Composed and decomposed strings stay distinct, and
  decimal strings such as `"1.00"` are never normalized. Domain-separated digests are
  `SHA-256(domain + "\n" + canonical bytes)`.
- `uv run python scripts/check_public_boundary.py` checks the stageable file list (and any wheel
  or sdist you pass) against an allowlist. Handoff material, imported history, environment files,
  corpora, model files, credentials, store or tooling directories and absolute or escaping paths
  are refused, as is anything not explicitly allowed.

### Array bounds in the exported schemas

The Pydantic models are the contract. For an array-valued field wrapped by a before-validator
(for example `allowedPlanDigests`, `inputRefs`, `limitsRefs`, `items`, `inputDigests`), Pydantic
emits the field's `min_length` / `max_length` as `minLength` / `maxLength`, which JSON Schema
applies to strings only. The schema export (`contracts/registry.py`, `_array_bounds`) rewrites
those to `minItems` / `maxItems` on every array-typed node, so a validator that has only the
published bundle, such as Ajv, enforces the same bounds as the Python models. The files in
`schemas/` are regenerated from that export; `tests/contracts/test_release_registry.py` fails if
they drift, and `tests/acceptance/test_public_package.py` fails if any exported array node carries
`minLength` / `maxLength` again. Fixtures such as `run-authorization-empty-plan-digests`,
`result-empty-input-digests` and `result-two-input-digests` in
`tests/fixtures/public/schema_parity.json` show an empty or over-length array rejected by both
languages. The exported schemas are not accepted or published yet; nothing here changes a
contract version.

## 4. Building and inspecting distributions

Build only into a private temporary directory, and inspect the archives with the boundary
checker. Nothing is uploaded and no CI deployment is configured. An offline build needs the
pinned build backend in the local uv cache (`uv build --offline`); without it the build is `blocked`.

```
out="$(mktemp -d)"
uv build --out-dir "$out"
uv run python scripts/check_public_boundary.py "$out"/*.whl "$out"/*.tar.gz
```

The wheel may hold only `conscience_foundry` modules, the ledger migration SQL and standard
metadata. The sdist adds only `pyproject.toml`, `README.md`, `LICENSE` and build metadata.

Imported historical documents and private handoff notes stay untracked and are excluded with exact
patterns in `.gitignore`. Stage by explicit path, never with a bulk add.

## 5. Isolated PostgreSQL requirements

Database tests and the `local_isolated_postgres` label require all of the following, checked by
`tests/conftest.py` before any connection:

- `CF_TEST_POSTGRES_DSN` and `CF_TEST_POSTGRES_APPROVED_DSN` are both set and identical. Neither
  alone is accepted.
- The DSN uses only `host`, `port`, `dbname`, `user` and `connect_timeout`.
- `host` is an absolute path to a private socket directory: owned by the current user, mode `0700`,
  and not a symbolic link. There is no network host.
- `dbname` matches `cf_<name>test<name>` (a disposable database) and `user` is set.
- No ambient libpq environment variable is present.
- Run database tests sequentially. Do not point this at a shared or real database.

Shape of the value: `host=<private-socket-dir> dbname=cf_<scope>_test user=<test-role>`.

## 6. Operator commands and scopes

`cfoundry` is an explicit command line. Stateful commands need `--config` (a private operator
file). A command with an effect is a dry run unless it gets `--execute` and a configured grant.
Each effect class has its own grant list; one never implies another.

| Grant class | Commands |
| --- | --- |
| admission | `admit` |
| execution | `prepare-run`, `authorize-run`, `dispatch`, `reconcile`, `cancel`, `pause`, `resume` |
| review | `review` |
| release | `build-release`, `import-release` |
| publication | `publish` |
| activation | `activate` |
| read | `read-span` |
| recovery | `backup`, `restore`, `retention-report` |
| pilot | `preflight`, `run-pilot` |

`validate` is read-only. Policy scopes are `read`, `remoteTransfer`, `extract`, `enrich`, `embed`,
`train`, `publish` and `auditMetadataRead`. Backup needs `read` and `auditMetadataRead`; a live
pilot needs `extract` and `remoteTransfer`. Selected-content permission is always required, and a
deny or unknown permission fails closed while every admission row is still reported.

## 7. Trust model notes

- **Backup manifest is unsigned.** The recovery manifest binds the snapshot, recovery point and
  copied references into one digest, but nothing signs it. Restore trusts the operator-supplied
  manifest and artifacts: whoever can write both the manifest and the objects can present a
  self-consistent backup. Independent storage and operator custody are the only protection. A
  restore always writes a durable pause barrier and clears local verification, so work after the
  recovery point is reconciled by an operator before dispatch resumes.
- **Pinned release and current authorization are different checks.** A slice response alone does not
  prove full-text content; local full-artifact verification is available, and network service and
  authentication are out of scope for F1.
- **No raw text, private path, credential or signed URL** belongs in logs, public test artifacts or
  any distribution. Credentials are runtime-injected, short-lived and scoped.

## 8. Live blockers

A paid live pilot cannot run until the operator supplies, from outside the repository, every one
of: provider, region, deployment, tariff, limits, run and attempt caps, a backup, an expiry and a
separately authorized grant bound to the digest of the exact preflight packet. Synthetic test
values (for example the 10 and 4 budget example) are never defaults or grants. Any missing value
is `blocked`.

`run-pilot` orchestrates `backup`, `prepare-run`, `authorize-run`, `dispatch` and `reconcile` and
stops there. It does not produce a private `local_verified` release: `review`, `build-release`
and `import-release` run separately under their own grants (the review and release classes above),
after the pilot's result exists. Completing the pilot steps is never acceptance by itself.

A grant is single-use, but that is enforced only by `run-pilot`: it creates an exclusive marker file
in a private directory beside the operator config before the first step. The ledger does not own
it, so deleting or copying that directory defeats it. Treat the config directory as the
authority.

## 9. Gates that are `not_run`

These are listed in the acceptance fixtures and in every preflight report. None of them is
evidence of success.

| Gate | Label | Why |
| --- | --- | --- |
| Paid provider round trip and an independent-medium restore (`GATE-live`) | `not_run` | Needs its own authorization and real infrastructure. |
| Consumer bridge coordinate conversion and export parity (`GATE-f2-bridge`) | `not_run` | Belongs to a later phase. |
| Enrichment anchoring, semantic review and replay (`GATE-f4-enrichment`) | `not_run` | Belongs to a later phase; F1 uses ordinary functions and deterministic fakes only. |
| Baseline and holdout leakage (`GATE-line-l`) | `not_run` | Belongs to a separate line of work. |

Carry-forward gates from the live-acceptance packet. The first three block live acceptance:

| Gate | Label | Meaning |
| --- | --- | --- |
| `staging_store_transfer` | `blocked` | No staging-to-store transfer exists. Verification reads only the local store, so a remote result cannot yet be verified and imported. |
| `executor_scoped_store` | `blocked` | The remote executor must be wired with a store scoped to the plan and attempt (a scoped executor store) before any live use. |
| `platform_restart_bound` | `blocked` | Platform crash restarts must be evidenced as bounded for the exact deployment. Zero retries and a finite timeout are not that evidence, so the Modal restart count is unbounded until concrete capability evidence exists. |

Only the first two can be attested closed, and only by trusted deployment code; neither a packet
nor any wire document can close them. Deferred minors stay visible as advisory items in every
report: manual-retry decisions are bound by time rather than attempt id (the pilot refuses manual
retry), `read-span` does not require a dry-run flag although it is not a dry run, a failed span
output write can leave its created file, the in-repository check is lexical, a ledger DSN may name
service or passfile files implicitly, orphan blobs can remain after a ledger refusal, remote call
ids are printed, and the cost estimate covers one attempt plus run storage but not more attempts.
