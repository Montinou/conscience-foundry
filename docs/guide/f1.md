# F1 guide: commands, evidence and open gates

This guide describes how to reproduce the F1 offline acceptance evidence, what that evidence does
and does not prove, and which gates are still `not_run`. It contains no real endpoint, credential,
tariff, path or account; every value shown is a placeholder in angle brackets.

## 1. Evidence labels

Every claim in a report or review carries exactly one label.

| Label | Meaning |
| --- | --- |
| `live` | Written or run while the live session was open: the one remote-function app that `run-pilot` holds around its `dispatch` and `reconcile` steps (section 8). It may reach a real service and incur real cost. |
| `synthetic_offline` | Ran in-process against synthetic fixtures and fake transports, or ran in a process where no live session was open. In a plain run it reaches no service, network, provider or real cost. In a live `run-pilot` it also labels the steps that run outside the session (see below), and those do real work. |
| `local_isolated_postgres` | Ran against a disposable local PostgreSQL that the operator explicitly authorized (section 5). Nothing else is reached. |
| `not_run` | Needs authority, infrastructure or a later phase that does not exist yet. It is never reported as success. |
| `blocked` | A prerequisite is missing (a locked dependency, a required value, a gate). The check stops; it is never skipped or replaced by a weaker check. |

The `live` label is never read from a document. It is derived from the evidence authority and the
live session the process itself holds (`evidenceLabel`): `live` only while that session is open,
`synthetic_offline` otherwise. Each step entry of a `run-pilot` report carries `evidenceLabel`, as
does the report (`live` when any step ran under the session, otherwise `synthetic_offline`), and so
do the control side's own observation and stop records. No operator document, request, plan,
packet or worker output has such a field: the strict models refuse one.

The label states the provenance of the evidence, not whether anything real happened. It says what
was attested under an open live session, and nothing more. It does not mean "no real effect". In a
live `run-pilot`, `prepare-run`, `authorize-run`, `reserve-storage` and `backup` run outside the
session and so carry `synthetic_offline`, yet they are real: `backup` writes to the remote backup
store, and the other three write budget, authorization and storage-reservation rows to the
operator's ledger. A pilot that halts before or after its session reports what it did, with the
step list gathered so far. If the session cannot be stopped when it closes, the report is still
`live` and says `unavailable`. A dry run reports no label because it records nothing.

Test outcomes are `pass`, `fail` or `not_run`. A command-line outcome is `ok`, `dry_run`,
`failed` or `blocked`. The `cfoundry` command exits 0 (ok or dry run), 1 (failed), 2 (usage) or 3
(blocked by a gate). The standalone parity tools use their own codes: `node tests/js/schema_parity.mjs`
and `scripts/check_schema_parity.py` exit 0 (parity holds), 1 (a check failed) or 2 (blocked by a
missing toolchain or dependency, or by a Node timeout in the Python wrapper); `scripts/check_public_boundary.py` exits 0 (boundary
holds) or 1 (a violation).

## 2. Locked toolchain

| Tool | Pin |
| --- | --- |
| Python | 3.12, with `uv` managing the environment from `uv.lock` |
| Build backend | `setuptools>=80,<81` |
| Python canonical JSON | `rfc8785>=0.1.4,<0.2` |
| Node | 22 or newer (`tests/js/package.json` `engines`) |
| JSON Schema validator (Node) | `ajv@8.20.0`, JSON Schema 2020-12 dialect |
| Canonical JSON (Node) | `canonicalize@5.1.0`, an RFC 8785 implementation separate from the Python one |

The Node tools are development-only, locked with exact versions and integrity hashes in
`tests/js/package.json` and `tests/js/package-lock.json`. `node_modules` is never committed.
Install from the lock with `npm ci` inside `tests/js` (use `npm ci --offline` when the packages are
already in the local npm cache). A missing dependency is `blocked`: the parity checker exits 2 (not 3, which is the `cfoundry` code) and
the Python wrapper raises `NodeToolchainBlocked`. It is never skipped, and a Python-only check
never stands in for it.

## 3. Verification commands

All of these are `synthetic_offline` unless stated otherwise.

```
uv run ruff check .
uv run mypy src/conscience_foundry
uv run pytest tests/acceptance/test_public_package.py -q
node tests/js/schema_parity.mjs
uv run python scripts/check_schema_parity.py
uv run python scripts/check_public_boundary.py [<wheel-or-sdist> ...]
uv run pytest                      # full suite; database tests need section 5
```

- `node tests/js/schema_parity.mjs` compiles every exported schema in `schemas/` with Ajv (the
  raw byte roles `cf.raw-original.v1` and `cf.canonical-text.v1` are exported as `{"not": {}}`:
  they compile but no JSON instance validates, so they are outside JSON-instance parity; the
  report lists them separately as `outsideInstanceParity`, and the Python checker asserts that
  exact set),
  validates the shared fixtures (`tests/fixtures/public/schema_parity.json`) and checks canonical
  bytes and SHA-256 digests against literal expectations. It imports no repository code.
- `uv run python scripts/check_schema_parity.py` runs the Node checker, runs the maintained
  Pydantic models over the same fixtures and fails on any disagreement. `semantic_invalid`
  fixtures are shape-valid JSON Schema instances that trusted semantic code rejects (for example an
  empty span, a lone surrogate or a cross-project reference); the split is asserted, not hidden.
  array length bounds are in the exported schemas (see "Array bounds in the exported schemas"), so
  an empty or over-length array is a plain `shape_invalid` fixture that Python and Ajv both reject.
  Ajv runs fully strict (`strict` and `strictTypes`), so a bound keyword on the wrong type fails
  compilation.
- Canonical JSON follows RFC 8785: object keys sort by UTF-16 code unit, so U+10000 sorts before
  U+E000 (code point order would reverse them). Composed and decomposed strings stay distinct, and
  decimal strings such as `"1.00"` are never normalized. Domain-separated digests are
  `SHA-256(domain + "\n" + canonical bytes)`.
- `uv run python scripts/check_public_boundary.py` checks the stageable file list (and any wheel
  or sdist you pass) against an allowlist. Handoff material, imported history, environment files,
  corpora, model files, credentials, store or tooling directories and absolute or escaping paths
  are refused, as is anything not explicitly allowed.

### Array bounds in the exported schemas

The Pydantic models are the contract. For an array-valued field wrapped by a before-validator
(for example `allowedPlanDigests`, `inputRefs`, `limitsRefs`, `items`, `inputDigests`), Pydantic
emits the field's `min_length` / `max_length` as `minLength` / `maxLength`, which JSON Schema
applies to strings only. The schema export (`contracts/registry.py`, `_array_bounds`) rewrites
those to `minItems` / `maxItems` on every array-typed node, so a validator that has only the
published bundle, such as Ajv, enforces the same bounds as the Python models. The files in
`schemas/` are regenerated from that export; `tests/contracts/test_release_registry.py` fails if
they drift, and `tests/acceptance/test_public_package.py` fails if any exported array node carries
`minLength` / `maxLength` again. Fixtures such as `run-authorization-empty-plan-digests`,
`result-empty-input-digests` and `result-two-input-digests` in
`tests/fixtures/public/schema_parity.json` show an empty or over-length array rejected by both
languages. The exported schemas are not accepted or published yet; nothing here changes a
contract version.

## 4. Building and inspecting distributions

Build only into a private temporary directory, and inspect the archives with the boundary
checker. Nothing is uploaded and no CI deployment is configured. An offline build needs the
pinned build backend in the local uv cache (`uv build --offline`); without it the build is `blocked`.

```
out="$(mktemp -d)"
uv build --out-dir "$out"
uv run python scripts/check_public_boundary.py "$out"/*.whl "$out"/*.tar.gz
```

The wheel may hold only `conscience_foundry` modules, the ledger migration SQL and standard
metadata. The sdist adds only `pyproject.toml`, `README.md`, `LICENSE` and build metadata.

Imported historical documents and private handoff notes stay untracked and are excluded with exact
patterns in `.gitignore`. Stage by explicit path, never with a bulk add.

## 5. Isolated PostgreSQL requirements

Database tests and the `local_isolated_postgres` label require all of the following, checked by
`tests/conftest.py` before any connection:

- `CF_TEST_POSTGRES_DSN` and `CF_TEST_POSTGRES_APPROVED_DSN` are both set and identical. Neither
  alone is accepted.
- The DSN uses only `host`, `port`, `dbname`, `user` and `connect_timeout`.
- `host` is an absolute path to a private socket directory: owned by the current user, mode `0700`,
  and not a symbolic link. There is no network host.
- `dbname` matches `cf_<name>test<name>` (a disposable database) and `user` is set.
- No ambient libpq environment variable is present.
- Run database tests sequentially. Do not point this at a shared or real database.

Shape of the value: `host=<private-socket-dir> dbname=cf_<scope>_test user=<test-role>`.

## 6. Operator commands and scopes

`cfoundry` is an explicit command line. Stateful commands need `--config` (a private operator
file). A command with an effect is a dry run unless it gets `--execute` and a configured grant.
Each effect class has its own grant list; one never implies another.

| Grant class | Commands |
| --- | --- |
| admission | `admit` |
| execution | `prepare-run`, `authorize-run`, `reserve-storage`, `dispatch`, `reconcile`, `cancel`, `pause`, `resume`, `record-billing` |
| review | `review` |
| release | `build-release`, `import-release` |
| publication | `publish` |
| activation | `activate` |
| read | `read-span` |
| recovery | `backup`, `restore`, `restore-drill`, `retention-report` |
| pilot | `preflight`, `run-pilot` |

Three commands are new in the live-readiness work:

- `reserve-storage --run-id <run> --amount <usd> --evidence <ref>` reserves the run's storage cost.
  The evidence is the reviewed cost estimate. It is refused while the run already holds an open
  storage reservation. Inside `run-pilot` its arguments are bound to the preflighted packet.
- `restore-drill --manifest <file> --drill-config <file> --evidence-output <new-file>
  --valid-for-seconds <n> [--attest-independent]` restores a backup into a fresh target derived
  from the drill config (a new ledger schema and object directory, never the live ones), verifies
  everything it restored, stores a drill report and writes the backup evidence the preflight
  packet binds. `independence` is `verified` only when the backup store is the remote
  object-storage kind (`backup_store.kind: r2`) and the operator passes `--attest-independent`;
  otherwise it is `unverified` and the preflight refuses it. The evidence file is created before
  the restore and removed on any failure. An incomplete recovery writes no evidence.
- `record-billing --attempt-id <attempt> --amount <usd> --evidence <ref>` records the one final
  settlement of an attempt as `actual`, from the operator's billing document
  (`cfoundry.billing-record.v1`, cited by reference from the local object store). It is refused
  unless that document belongs to the configured project and that attempt, was recorded by the
  authorizing operator, is `actual`, and names exactly the amount requested. A recorded
  settlement is never revised, and an attempt that may still be running is refused
  (`dispatch_unknown`). It is a standalone command, not a pilot step.

`validate` is read-only. Policy scopes are `read`, `remoteTransfer`, `extract`, `enrich`, `embed`,
`train`, `publish` and `auditMetadataRead`. Backup needs `read` and `auditMetadataRead`; a live
pilot needs `extract` and `remoteTransfer`. Selected-content permission is always required, and a
deny or unknown permission fails closed while every admission row is still reported.

### Profile metadata schema (`admit`)

By default `admit` accepts exactly what F1 accepted: the built-in technical profile, whose
`metadataSchemaRef` must be the installed `cf.technical-metadata.v1` schema; any other profile
reference is refused as `unsupported_schema`.

A second profile validates item metadata against a schema file of the operator's own. Set
`admission.profileMetadataSchemaPath` in the private config to the absolute path of that file
(a regular file you own that others cannot write) and have the profile's `metadataSchemaRef` pin
its exact bytes: `artifactSchema` `cf.metadata-schema.v1`, plus the file's SHA-256 digest and size.
A profile that pins the technical schema is still accepted with a file configured (the file is
not read). Otherwise `admit` refuses the file as `hash_mismatch` unless its digest and size equal
the pin, and as `unsupported_schema` unless the pin names `cf.metadata-schema.v1`. A reference
that is neither the technical schema nor the configured file is `unsupported_schema` when no file
is configured; when one is, the file is the only candidate, so a reference it does not match
(stray, or the file edited since it was pinned) is `hash_mismatch`. Each item's metadata
is then checked against the file, and one item that does not conform refuses the whole manifest as
`invalid_schema` before any admission row exists. The admitted `SourceAsset` carries the item's
metadata unchanged.

The file is a JSON-Schema-shaped document restricted to a closed subset: `type: "object"`,
`additionalProperties: false`, `required`, and `properties` of `string` (`maxLength` of at most
1024 is required; `pattern` and `enum` are optional), `integer` (`minimum`, `maximum`), `boolean`,
or one nested object of the same form (depth at most 2), with at most 64 properties per object.
`$ref`, `$id`, `$schema`, `format`, arrays, numbers and every other keyword are outside the subset
and refused as `invalid_schema`; in particular a `$schema` keyword is refused, so leave it out.

`cf.metadata-schema.v1` is a new registered schema id. An existing install reinstalls the contract
set (so the bundle lists the new schema) and adds a limits entry for `cf.metadata-schema.v1` to its
limits file; without them `admit` with a schema file configured fails closed.

## 7. Trust model notes

- **Backup manifest is unsigned.** The recovery manifest binds the snapshot, recovery point and
  copied references into one digest, but nothing signs it. Restore trusts the operator-supplied
  manifest and artifacts: whoever can write both the manifest and the objects can present a
  self-consistent backup. Independent storage and operator custody are the only protection. A
  restore always writes a durable pause barrier and clears local verification, so work after the
  recovery point is reconciled by an operator before dispatch resumes.
- **Pinned release and current authorization are different checks.** A slice response alone does not
  prove full-text content; local full-artifact verification is available, and network service and
  authentication are out of scope for F1.
- **No raw text, private path, credential or signed URL** belongs in logs, public test artifacts or
  any distribution. Credentials are runtime-injected, short-lived and scoped.

## 8. Live blockers

A paid live pilot cannot run until the operator supplies, from outside the repository, every one
of: provider, region, deployment, tariff, limits, run and attempt caps, a backup, an expiry and a
separately authorized grant bound to the digest of the exact preflight packet. Synthetic test
values (for example the 10 and 4 budget example) are never defaults or grants. Any missing value
is `blocked`, with a named error. A `live` config section has no defaults and requires
`project_max_live_attempts`; its credentials are read from environment variables whose names the
config gives, and never appear in a log, error, `repr`, record or report.

`run-pilot` orchestrates `backup`, `prepare-run`, `authorize-run`, `reserve-storage`, `dispatch` and
`reconcile` and stops there, in that order (`reserve-storage` only after `authorize-run` and
before `dispatch`). The reconcile step may name the attempt `@dispatch`, which stands for the
attempt the dispatch step returned. It does not produce a private `local_verified` release:
`review`, `build-release` and `import-release` run separately under their own grants (the review
and release classes above), after the pilot's result exists. Completing the pilot steps is never
acceptance by itself, and every report says `paidPilotAcceptance: not_established`.

With a `live` section the remote session is held by `run-pilot` alone. It is opened before the
first `dispatch` or `reconcile` step and exited after the last one, on every exit. A standalone
`dispatch` against a live config is refused (`live_requires_pilot`), and so is any other
standalone command that needs the live evidence authority. `record-billing` is the exception: it
attests only the operator's billing document. Each call has a deadline made of the scheduling,
startup, execution and cancel-margin bounds, which must fit the plan's wall limit. At the deadline,
or on Ctrl-C, the attempt is cancelled through the ledger with the reason `limit_exceeded`; a
cancel that cannot be confirmed leaves `unknown_outcome`. It is never `failed` or `succeeded`, and
the attempt is never left running. Ctrl-C ends the pilot with exit code 130 (`interrupted`).

A grant is single-use, but that is enforced only by `run-pilot`: it creates an exclusive marker file
in a private directory beside the operator config before the first step. The ledger does not own
it, so deleting or copying that directory defeats it. Treat the config directory as the
authority.

Residual risks, stated in the `residual_risks` list of every `run-pilot` report:

- controller death leaves `unknown_outcome`: this process cannot settle a call it no longer holds;
- a crash before `publish_result` loses a paid result;
- costs stay `estimated` until billed. A pilot is not accepted while any cost is `estimated`;
  `record-billing` turns a cost into `actual` from the billing document.

A pilot whose attempt was cancelled at its deadline reports its steps as settled, not as a
result, and acceptance stays `not_established`.

## 9. Gates that are `not_run`

These are listed in the acceptance fixtures and in every preflight report. None of them is
evidence of success.

| Gate | Label | Why |
| --- | --- | --- |
| Paid provider round trip and an independent-medium restore (`GATE-live`) | `not_run` | Needs its own authorization and real infrastructure. |
| Consumer bridge coordinate conversion and export parity (`GATE-f2-bridge`) | `not_run` | Belongs to a later phase. |
| Enrichment anchoring, semantic review and replay (`GATE-f4-enrichment`) | `not_run` | Belongs to a later phase; F1 uses ordinary functions and deterministic fakes only. |
| Baseline and holdout leakage (`GATE-line-l`) | `not_run` | Belongs to a separate line of work. |

Carry-forward gates from the live-acceptance packet. The first three block live acceptance. Each
is closed by trusted code, and stays `open` (the preflight is not ready) while that code is
missing. One of them, `platform_restart_bound`, is closed by the capability record, which is
evidence carried in the packet; a record alone does not close it, because trusted code checks it
against the deployed code, image and SDK before any step:

| Gate | State | What closes it |
| --- | --- | --- |
| `staging_store_transfer` | `closed` by the live wiring | Inputs are staged to the object-storage staging area, and an attempt-scoped staging reader returns the result, which is imported into the local store and re-verified before acceptance. The preflight probes the reader against two synthetic attempts. |
| `executor_scoped_store` | `closed` by the live wiring | The remote executor reads through a store scoped to the plan and attempt (a scoped executor store), and the credential issuer reports exactly the plan's read keys and the attempt's write prefix. Staging credentials are two short-lived grants per attempt, read-only first and read-write second. |
| `platform_restart_bound` | `closed` by the capability record | The deployment's capability record states `platform_restart_bound = bounded` with zero platform restarts, cancellation that terminates containers and deadline enforcement at entry and at every bounded step. Zero retries and a finite timeout alone are not that evidence. `run-pilot` checks the record against the deployed code, image and SDK before any step. |

Only the first two can be attested closed, and only by trusted deployment code (the runtime
wiring itself, `attested_gates`); neither a packet nor any wire document can close them. One
execution per attempt is enforced in the container by a lease and a result pointer under the
attempt's staging prefix: a second container that loses the lease returns the winner's result or
`{"duplicate": true}`. A cap on live attempts for the whole project (`project_max_live_attempts`)
is checked by the ledger. Deferred minors stay visible as advisory items in every
report: manual-retry decisions are bound by time rather than attempt id (the pilot refuses manual
retry), `read-span` does not require a dry-run flag although it is not a dry run, a failed span
output write can leave its created file, the in-repository check is lexical, a ledger DSN may name
service or passfile files implicitly, orphan blobs can remain after a ledger refusal, remote call
ids are printed, and the cost estimate covers one attempt plus run storage but not more attempts.

## 10. Rollout order

Each step runs once, stops on any blocker or unknown outcome, and keeps every value (credentials,
buckets, accounts, paths) outside the repository. Nothing here is automated.

1. Create the staging parent credential and a separate backup credential, each limited to its own
   bucket, and export them under the environment variable names the config gives.
2. Probe the staging store with a one-object write that carries a SHA-256 checksum. The result
   sets `checksum_mode` (`sha256_header` if accepted, otherwise `readback`).
3. Set a spend limit on the provider workspace and record whether a billing report is available.
4. Write the live config (the `live` section, `project_max_live_attempts: 1`, `backup_store.kind:
   r2`, the policy and the intake manifest) and the drill config. Run `admit` and `prepare-run`
   with `--execute`.
5. `backup`, then `restore-drill ... --attest-independent`. The evidence must say
   `independence: verified`.
6. `preflight` with the packet and every evidence file. It must be ready with all three blocking
   gates closed.
7. `run-pilot` with one attempt: `backup`, `prepare-run`, `authorize-run`, `reserve-storage`,
   `dispatch`, `reconcile --attempt-id @dispatch`. The result must be `verified` and its cost
   within the packet's cap.
8. `review`, `build-release` and `import-release`, each under its own grant, ending in
   `local_verified`.
9. A second `backup` and `restore-drill`. It must be `verified` and must not change the release.
10. `retention-report` with no deletion, then record the live evidence and the cost
    (`record-billing` with the operator's billing export). Live acceptance is recorded as passed
    only when no cost is left `estimated`.
